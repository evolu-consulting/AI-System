# 2026-08-21 — Policy action table (v6.5): deterministic policy routing

## What changed

Added a deterministic policy tier beside the existing semantic one. Policy rules now live as
rows keyed by `(action, sub_action)` in KH's own `hooks.db`, so routing a request to its
governing policy is a `SELECT` instead of a cosine-similarity guess.

New files:

- `app/policy_actions/__init__.py`, `store.py`, `api.py` — the subsystem (modelled on
  `app/hooks/`: same SQLite file, same deterministic-by-design contract).
- `seeds/policy_action_table.seed.json` — generated seed payload, 2 actions / 22 rules.
- `tests/test_policy_actions.py` — 22 mechanism checks.
- `docs/policy-action-table.md` — current-state documentation.

Changed:

- `main.py` — attaches `app.policy_actions` right after `app.policy`.

New endpoints: `GET /policy/actions`, `GET /policy/actions/raw`, `GET /policy/plan`,
`GET /policy/rule`, `POST /policy/action/set`, `POST /policy/rule/set`,
`POST /policy/rule/delete`, `POST /policy/action/delete`, `POST /policy/actions/bulk`.

## Why

`/policy/match` embeds the request and takes the nearest policy vector. Measured on 65 probes at
the tuned threshold 0.76: 60/65 correct, false fires on the fragments `source code repo project`
and `code`, and a miss on every untranslated Vietnamese request — the embedder is
`bge-small-en-v1.5`, English only. The false-fire and true-positive bands overlap, so no
threshold is clean. ~2000 ms per call because the model runs.

fen's design replaces the guess with an exact lookup, one row per small step inside a big action
group. Two families can no longer bleed (`read files` exists under both `scan code` and
`review code` as two different rules), there is no threshold to tune, and language stops
mattering because the agent maps meaning to an English label instead of having its sentence
embedded.

## Decisions taken

- **Storage: KH's own `hooks.db`, not a new side file** (fen's call — reuse the SQLite already
  there). Chroma's `chroma.sqlite3` was rejected: third-party schema we do not own.
- **Implemented inside the server and rebuilt**, rather than shipping a side database plus a
  helper script the hook shells out to. The earlier handoff assumed no source was available; the
  source is at `C:/Workspaces/Personal/RWorkspace/Slaves/KnowledgeHub`, so the table gets proper
  endpoints, one source of truth, and no machine-specific path baked into a shared hook file
  (coding rule 3.4).
- **`none` is a first-class answer.** Unknown labels are 404 `UNKNOWN-ACTION` / `NO-RULE` with
  the valid labels listed. Never a nearest-neighbour fallback.
- **The vector tier stays** as a fallback for requests whose action label is unclear (Never-Worse
  rule 3.3: nothing that worked before stops working while only two families are in the table).
- **Migration is lossless**: one row per numbered clause of the two live policy bodies, 33/33
  clauses covered, provable at any time with `policy_table.py verify`.

## Verification

- `tests/test_policy_actions.py` — 22/22 pass. Asserts the shared sub-action name resolves to two
  distinct rules, unknown action/sub-action fail loudly with the real labels listed, a
  pre-existing `hook_rules` row is untouched, an undeclared-action payload is rejected whole, a
  populated action refuses deletion, re-seeding is idempotent.
- `policy_table.py verify` — re-fetches the live policy bodies from `/policy/list` and confirms
  every clause tag is still claimed by a row: `review code` 24/24, `scan code` 9/9.
- Direct SQLite lookup: 0.82 ms including opening the connection, versus ~2046 ms for
  `/policy/match`.

## Honest caveat, carried forward

The classifier in this design is the agent picking a label from the menu, not an algorithm. The
prototype's 65/65 is self-graded. It is the real runtime mechanism, so the comparison is
meaningful, but it is not an independent benchmark; the tests above deliberately assert only
what is objective.

## Follow-ups not done here

- Update the live `UserPromptSubmit` / `intent-policy-guard` hook to consult the table first
  (text is generated by `policy_table.py hook-text`; installing it is a separate, reversible
  step).
- Decide whether the vector tier is eventually retired or stays as the permanent fallback.
- Migrate any further policy families as they appear.

# 2026-08-21 (later the same day) — follow-ups: vector route retired, project column added

Two changes fen asked for after the first cut shipped. Same feature, same files.

## 1. The semantic route is retired for ROUTING

The first cut kept `/policy/match` as a fallback for requests whose action label was unclear.
Within the day it false-fired on a real request: *"store all information from a tools folder into
a KH project as a detailed work log"* scored `0.826` against the code-scan family
(`policy_code_scan_v3_s03`, intent row "Ingest a project's source files into KH") and would have
turned a work-log task into a codebase scan. The action table answered correctly — no label fits.

Because the false-fire band and the true-positive band overlap, no threshold removes that class
of error, so the fallback was removed rather than re-tuned:

- `UserPromptSubmit` / `intent-policy-guard` STEP 3 now says: answer `none` and do the work; do
  not call `/policy/match`.
- `SessionStart` / `kernel` clause (1) "CONSULT KH … POLICY-FIRST" now routes through
  `GET /policy/actions` + `GET /policy/plan` instead of `POST /policy/match`, and its `kh.ps1`
  usage example no longer points at `/policy/match`.
- Both old hook texts are backed up in `policy_hook_backup` in `hooks.db`.
- `/policy/match`, `/policy/add`, `/policy/list` and the policy vector collections are untouched
  and still live; they are simply no longer consulted to decide a deliverable.

## 2. Policy rules carry a `project`

`policy_actions` is now keyed `(project, action)` and `policy_rules` `(project, action,
sub_action)`. Rules that belong to no single project, or to all of them, carry the sentinel
`every project`; both seeded families are that tier, since both came from orchestrator-common.

- Reads consult the active project first and fall back to `every project` **per sub-action**, so
  one step of a common action can be overridden without copying the other nine.
- A project may also declare actions of its own; those stay invisible to the common menu and to
  other projects, which get `404 UNKNOWN-ACTION` for them.
- Every read/write endpoint takes `project`; writes default to `every project`. New:
  `GET /policy/actions/projects`.
- **The caller never types the sentinel and never filters results** — resolution is server-side,
  so there is no scope reasoning on either side of the call. That is also why the sentinel is a
  real value rather than blank: in a `NOT NULL` column, blank would make "applies everywhere"
  indistinguishable from "the project was lost on the way in", and the silent failure direction
  would be a project rule leaking everywhere. The injected menu prints `[project: X]` only for
  project-specific rows, so common rules cost no extra tokens in the hook.
- Migration: SQLite cannot alter a primary key, so `store.init()` renames, recreates and copies
  each pre-column table, tagging existing rows `every project`. Idempotent, and mirrored in
  `policy_table.py build` so whichever side runs first does the work.

## Verification

`tests/test_policy_actions.py` grew from 22 to **42 checks, all passing**: per-project override
of one step, the other nine still resolving from common, an unrelated project still getting the
common rule, project-only actions hidden from the common menu and 404 for other projects,
deleting an override falling back, and a pre-column table migrating with its content intact and
tagged `every project`. `policy_table.py verify` still reports 33/33 clauses covered.

# 2026-08-21 (third pass) — mechanism v3: intent → project → policy

fen specified the retrieval mechanism end to end: *"1. receive intent → ask orches whether there
is a project; when a project is initialised its metadata is added into the orchestrator's C4 tree.
2. besides the action, no project → query policy with project = every; with a project → query by
(project or every). 3. other steps if needed."* Asked how step 1 should resolve, he chose a
literal match over the C4 nodes rather than a vector search.

## What changed

- `app/projects.py` — project identity is published into the **orchestrator's C4 tree** at init:
  `POST /projects` now also writes one C4 L1 record (`project_registry__<id>`, tree
  `c4_project_registry`, lv 1) carrying role, aliases, keywords, descriptor and the folded terms.
  A failed embed never fails creation; the reply says to run the sync. New: `registry_entries`,
  `upsert_registry_entry`, `sync_orchestrator_registry`, `match_projects`,
  `resolve_project_name`, `canonical_or_none`, plus `GET /projects/registry` and
  `POST /projects/registry/sync`.
- `app/orchestrator.py` — `GET /orchestrator/project_match?text=` is step 1. Literal, accent- and
  case-insensitive, word-boundary matching; returns `best`, `ambiguous`, `policy_project` and
  every candidate with the term that hit.
- `app/policy_actions/api.py` — every `project` parameter is canonicalised through the registry,
  so an alias or keyword works; replies echo `requested_project`.
- `main.py` — startup syncs the registry from the manifest (idempotent, embeds nothing unless a
  project's names changed).
- Hook texts regenerated: `UserPromptSubmit`/`intent-policy-guard` v3 and the `SessionStart`
  kernel clause now describe the two lookups in fen's step order. Previous texts are in
  `policy_hook_backup`.

## Traps worth remembering

- `from __future__ import annotations` makes route annotations strings resolved in **module**
  scope: importing `Request`/`Query` inside `attach()` made FastAPI treat `request: Request` as a
  query parameter and `POST /projects` started returning 422. Import them at module level.
- FastAPI matches routes in registration order, so `/projects/registry` must be registered
  **before** `/projects/{project_id}` or the dynamic route swallows it.
- A fresh `_internal` copy costs ~1–2 minutes of cold start (72–180 s measured), almost all of it
  in "[1/3] Loading embedding model" while the OS reads the newly written files. Not a hang.
