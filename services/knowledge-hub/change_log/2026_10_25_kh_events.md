# KH events: EventStore port, in-house queue, kh-events sidecar, KH's own events (2026-10-25)

## Why

A day on machine A left machine B knowing about 25% of it (2026-10-24). Part of the cure is a full record of what
each session did: every API call, turn, message and worklog, with the person, the session and the project. The
store must be swappable (Rowan: interfaces, plug-in and plug-out), and a burst must never hit the database head
on.

## Choices (Rowan, 2026-10-24)

- **Store**: HANA, behind an interface. ClickHouse, Druid, Pinot, TimescaleDB and InfluxDB are not offered on
  this BTP account. HANA Cloud's column store holds tens of millions of rows at no extra cost.
- **Buffer**: KH's own queue. RabbitMQ was checked first and cannot work here:
  - Docker apps run, but AMQP needs TCP and the account has no TCP route.
  - Our role cannot add container-to-container network policies.
  - Container disks are lost on restart.

## How

- **`app/eventing/store.py`: `EventStore` port.**
  - Methods: append (gapless seq per namespace, first copy of a repeated id kept, optional guard inside the
    transaction), read, get, stats, count_kind.
  - Adapter `sql` is the default. It is `kh_event` in KH's relational store: HANA on BTP, sqlite locally.
  - `KH_EVENT_STORE` picks the adapter. A columnar store is one more class with the same methods.
- **`app/caps/events.py`**: the /v1 event routes (DLC namespaces) validate and fence as before, and store through
  the port.
- **`app/eventing/queue.py`: `EventBuffer` port.**
  - `direct`: straight to the store.
  - `memory`: a bounded queue with one writer thread. It writes batches grouped by namespace, puts a refused
    batch back at the front, and drains on stop. When full it refuses with `QueueFull`.
  - `http`: posts to the sidecar.
  - `KH_EVENT_BUFFER` picks the buffer. The default is `http` when `KH_EVENTS_URL` is set, else `direct`.
  - Delivery is at least once.
- **`app/eventing/sidecar.py`: the `kh-events` instance.**
  - `POST /queue/publish`, bearer `KH_EVENTS_TOKEN`: 202, or 503 + Retry-After when full.
  - `GET /queue/stats` and `/health`.
  - Manifest: `deploy/btp/kh-events/manifest.yml`. It uses the same staged build and the same HANA schema.
  - KH reaches it over its HTTPS route.
- **`app/eventing/emit.py`: KH's own events.** They go to namespace `kh`, are off unless `KH_EVENTS=on`, and
  never block or break a request. They pass through a bounded outbox with a flusher thread; the oldest are
  dropped and counted past `KH_EVENTS_OUTBOX_MAX`.
  - Kinds: `kh.api.call` (method, path, status, ms, hook_type), `kh.session.turn` (bound project),
    `kh.message.sent`, `kh.message.delivered`, `kh.worklog.stored`.
  - Columns: `session_id` = X-KH-Actor, `ix_s1` = e-mail, `ix_s2` = path, `ix_n1` = ms.
  - Read with `GET /events` and `/events:stats` (maintainers).
- **DLC events through the queue**: set `KH_EVENTS_BUFFERED_NS` to the namespaces (or `*`).
  - Their unfenced batches answer 202 with `queued: true` and no seq, and are stored within about a second.
  - Fenced kinds always write straight through, inside the lease check.
  - Off by default, because a DLC client that needs the seq in the answer would break.

## Not yet

`app/caps/outbox.py` and `app/caps/outcomes.py` still read `kh_event` with SQL of their own (cursors inside their
transactions). They work on the `sql` adapter only. Moving them behind the port is the next step before a
non-SQL store.
