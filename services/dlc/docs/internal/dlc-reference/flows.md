# The three standard flows: New System, Enhancement, Bug Fix

The engine has **one** pipeline. The three flows differ only in what goes in: the spec pack and
the target repository. A caller prepares those two, then starts a run. Custom flows are out of
scope for now.

| Flow | Target repository | Spec pack content |
|---|---|---|
| New System | new empty git repo (or none: the engine creates one) | the whole system, one `## F<n>` section per feature |
| Enhancement | existing git repo | only the new or changed behaviour |
| Bug Fix | existing git repo | one F-item built from title, repro, expected, actual |
| Feature Migration (flow 4) | the v2 repo (rewrite) | generated by the engine from a v1 -> v2 feature parity analysis; see [feature-migration.md](feature-migration.md) |

## 1. Common contract

### 1.1 Spec pack (a directory on the engine host)

```
<pack>/
  pack.json      required
  spec.md        required (any .md / .txt files listed in pack.json are read too)
```

`pack.json`:

```json
{
  "id": "todo-cli",
  "title": "Todo CLI",
  "template": {"required": ["spec.md"]},
  "files": ["spec.md"]
}
```

- `required` (or `template.required`): files that must exist and be non-empty, else
  `SPEC_MISSING_FILE`.
- `files`: files to ingest; default = required + every `.md`/`.txt` under the pack (hidden dirs and
  `dry/` skipped). Only `.md` and `.txt` are readable; convert PDFs or docs first.
- The pack is content-addressed: any byte change is a new version.

### 1.2 Writing `spec.md` so the engine can work with it

- One section per feature: `## F1 <name>`, `## F2 <name>` ... Each F-item gets its own acceptance
  tests and its own QAS verdict.
- Under each F-item, testable criteria: inputs, outputs, exit codes, **error messages verbatim**.
  Readers keep only claims they can quote literally, so vague text produces no tests.
- Shared sections (interface, storage, conventions) go before the F-items; every F-item may use
  them.
- Say where data comes from (user input, another system). With `LINE_FGRAPH=1` anything consumed
  that nothing produces becomes a question instead of a guess.
- Target stack today: Python with `unittest`. Name the package and how the program is run.

Example: `line/samples/todo-pack/spec.md`.

### 1.3 Target repository

- A git repository with branch `main` checked out and **no uncommitted changes**
  (else the run escalates with `STATE_CONFLICT`).
- Must be reachable on the engine host's filesystem. A non-existent or empty directory is
  initialised as a new repo.
- The engine commits the locked acceptance tests to `main` (`tests/acceptance/`), works on
  branches `line/<run>/<unit>`, and fast-forwards `main` per merged unit. Point it at a working copy
  you are willing to let it commit to; push upstream yourself after review.

### 1.4 Start, watch, finish

```
POST /api/runs  {"pack": "<abs pack dir>", "target": "<abs repo dir>"}   -> 202 {"run", "state": "admitted"}
GET  /api/runs/{run}                                                      -> state, units, gates, budget, qas
GET  /api/runs/{run}/questions                                            -> parked? open questions
POST /api/runs/{run}/answers {"who": "...", "answers": [{"qid","option","text"?}]}
POST /api/runs/{run}:cancel  {"reason": "..."}
```

CLI equivalent: `python -m line.cli run <pack> --target <repo>` (blocks; exit 0 green, 1 escalated).

Poll loop for a caller: until `run.state` is `green` or `escalated`, every 15-30 s read
`GET /api/runs/{run}`; if `GET /api/runs/{run}/questions` says `parked: true` with open questions,
hand them to a person (or set `LINE_HUMAN_MODE=decide`).

**Done criteria (all flows):** run state `green` = every F-item's acceptance tests passed
`qas_repeats` times on the QAS copy of `main`, the regression pass over the other tests found in
the tree passed, and every unit is merged into the target's `main`. `escalated` = stopped with a
code (see [pipeline.md](pipeline.md#9-error-codes)); worktrees are kept as evidence.

Outputs: commits on the target's `main` (tests first, then one per merged unit), the QAS copy under
`LINE_WORKROOT`, events and records in the store, the board, `quarantine.json` for flaky tests.

## 2. New System

**Inputs**

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | system name (used for pack id and target folder) |
| `spec` **or** `pack` | one of them | spec text (becomes `spec.md`) or an existing pack directory |
| `target` | no | empty dir for the new repo; omitted = `<LINE_WORKROOT>/<run>/_target` |

**Steps for the caller**

1. Build the pack: write `spec.md` and `pack.json` (1.1) into a new directory; or use `pack`.
2. Optional: create the target repo yourself (`git init`, branch `main`, one initial commit with a
   `.gitignore` for `__pycache__/`, `*.pyc`, `.venv/`).
3. `POST /api/runs {"pack", "target"?}`, then watch (1.4).

**Engine path:** all stages, starting from an empty (or initial-commit) `main`.

**Verified:** end to end with real models on the sample pack (green, QAS 3/3).

## 3. Enhancement

**Inputs**

| Field | Required | Meaning |
|---|---|---|
| `target` | yes | existing git repo, clean, on `main` |
| `spec` | yes | the new or changed behaviour only, as F-items |
| `name` | no | label for the pack (default `enhancement`) |

**Steps for the caller**

1. Check `target` is a git work tree (`git -C <target> rev-parse --is-inside-work-tree`).
2. Build the pack from `spec` (1.1).
3. `POST /api/runs {"pack", "target"}`, then watch.

**Engine path:** same stages. The planner gets a map of the existing repo, builders change the
existing code inside their claims, and the regression net is: the merge queue re-runs the
acceptance tests of every unit merged in this run; QAS runs every other `unittest` in the tree as
the pseudo F-item `REGRESSION`. Existing behaviour therefore stays protected only as far as the
repo's own tests cover it.

Spec advice: state what must stay unchanged, and refer to existing commands/outputs verbatim.

## 4. Bug Fix

**Inputs**

| Field | Required | Meaning |
|---|---|---|
| `target` | yes | existing git repo, clean, on `main` |
| `title` | yes | one-line bug title |
| `repro` | yes | steps to reproduce |
| `expected` | yes | what should happen |
| `actual` | yes | what happens today |
| `context` | no | extra background (module, logs, constraints) |
| `name` | no | label (default: `title`) |

**Steps for the caller:** turn the fields into a one-F-item spec, build the pack, start the run.
The template the reference helper uses:

```markdown
# Bug fix: <title>

<context>

This is a bug fix on the existing code in this repository. Keep every other behaviour exactly as it is.

## F1 <title>

Steps to reproduce:

<repro>

- Expected: <expected>
- Today it does: <actual>
- After the fix, the steps above give the expected result, and the behaviour the existing tests cover is unchanged.
```

**Engine path:** same stages; one F-item, usually one unit. The acceptance test encodes the
expected behaviour; the regression pass guards the rest.

## 5. Reference caller (optional)

`line/tools/dlc_flow.ps1` (PowerShell 7) implements the caller side of all three flows for any
orchestrator that can run a shell step. Inputs come from environment variables so specs with quotes
or newlines are safe:

| Mode | Env inputs | Output (one JSON line) |
|---|---|---|
| `new` | `DLC_NAME`, `DLC_SPEC` or `DLC_PACK` | `{ok, process, pack, target}` (creates a fresh target repo) |
| `enhance` | `DLC_TARGET`, `DLC_SPEC`, `DLC_NAME`? | `{ok, process, pack, target}` |
| `bug` | `DLC_TARGET`, `DLC_TITLE`, `DLC_REPRO`, `DLC_EXPECTED`, `DLC_ACTUAL`, `DLC_CONTEXT`?, `DLC_NAME`? | `{ok, process, pack, target}` |
| `wait` | `DLC_RUN`, `DLC_WAIT_HOURS`? or `DLC_WAIT_MIN`? (40 min) | `{ok, done?, run, state, parked, questions?, summary?, spent_usd?, board}` |
| `migrate` | `DLC_V1`, `DLC_V2` (a repository or a folder of repositories), `DLC_V1_REPOS`?, `DLC_V2_REPOS`? (repository list files), `DLC_V1_REF`?, `DLC_V1_BASE`?, `DLC_V2_REF`?, `DLC_NOTES`? (.md), `DLC_MIG_MODE`? (ask), `DLC_SCOPE`?, `DLC_BUILD`? (true) | `{ok, process, v1, v2, mode, v1_ref, v1_base, v2_ref, v1_repos, v2_repos, notes, scope, build}` = the body of `POST /api/migrations` |
| `migwait` | `DLC_MIGRATION`, `DLC_WAIT_HOURS`? (12) or `DLC_WAIT_MIN`? | `{ok, done?, migration, state, parked, code, message, run, report, questions, summary, next, board, spent_usd}` (the same keys every time); parked = exit 3 with the open questions |
| `migresume` | `DLC_MIGRATION`, `DLC_MAX_USD`?, `DLC_MAX_USD_REPO`?, `DLC_RESCAN`? | `POST /api/migrations/{id}:resume`, then the same as `migwait` |

`DLC_HOME` (default `~/dlc`) holds `packs/` and `targets/`; `DLC_LINE_URL` defaults to
`http://127.0.0.1:8796`. Exit codes: 0 done / green, 2 bad input, 3 parked on questions,
4 escalated, 5 still running at the time limit. Waits poll with backoff (15 s doubling to 5 min). A wait
result carries `done: true` only for 0 and 3: a workflow that requires `done` treats parked as a successful
stop (tell a person, stop waiting) and escalated / time limit as a failure.

A three-step orchestration per flow is enough: **prepare** (`dlc_flow.ps1 -Mode <flow>`) ->
**start** (`POST /api/runs` with `pack` and `target` from the JSON) -> **wait**
(`dlc_flow.ps1 -Mode wait`). Fail the flow when prepare or start fails.
`line/tools/import_dlc_flows.py` is an example importer for one particular workflow tool; it is
not needed by the engine.

## 6. Known limits per flow (2026-10-11)

- Enhancement and Bug Fix run on the same verified engine path as New System, but no live
  real-model run of these two flows is recorded yet (**unverified**).
- The test author prompt assumes the implementation does not exist yet, and the "red on empty"
  gate runs tests against an empty scratch dir, not against the current target. Nothing checks that
  a bug-fix test is red on the **current** code before the fix (**open**).
- Acceptance test files are named per F-item (`tests/acceptance/test_f<n>.py`); a later run on the
  same target whose F-ids repeat can overwrite an earlier run's acceptance file (**open**, read
  from `understand/test_author.py`, not reproduced; use
  distinct F-ids or move earlier acceptance tests into the regular test suite).
- Impact analysis for Enhancement (which existing features a change touches) is not implemented;
  the feature graph is kept per run only.

## 7. Feature Migration (flow 4)

For a customer who moves from an old product version (v1) to a rewrite (v2) with the same business features
but different code. The engine inventories both, pairs features by behaviour, re-checks every one-sided
finding, builds a parity matrix (v1 only / v2 only / same / conflicting, custom features flagged), asks a
person about conflicts (or, in `decide` mode, keeps v2 with a backup and a log), measures the blast radius,
runs the v2 suite as a baseline, builds the missing features as an enhancement run on v2 and runs the suite
again. Full description, inputs and limits: [feature-migration.md](feature-migration.md).

**Inputs:** `v1`, `v2` (git repos; v2 on `main`, clean), optional `v1_ref`, `v1_base` (vanilla v1 ref),
`v2_ref`, `notes` (.md), `mode` `ask|decide`, `scope`, `build`.

**Caller steps:** `dlc_flow.ps1 -Mode migrate` -> `POST /api/migrations` with its JSON -> `dlc_flow.ps1 -Mode
migwait` (exit 3 = parked: answer on the board's Migrations tab or with `POST /api/migrations/{id}/answers`,
then `-Mode migresume` waits again). A migration can run for hours: `DLC_WAIT_HOURS` (default 12) bounds one
wait; running out of it is exit 5, and `migresume` / `migwait` simply wait again. Budget caps `max_usd` /
`max_usd_repo` (see feature-migration.md 4.1); a migration stopped on `MIGRATION_BUDGET` continues with
`migresume` and a raised `DLC_MAX_USD` / `DLC_MAX_USD_REPO`.

**Outcome of a caller flow:** green / analysed = success; parked = success with `parked: true`, the questions,
a summary and the board URL (the caller stops waiting); escalated or time limit = failure carrying `state`,
`code` and `next` (what to do). To continue, run the flow again with only `migration=<id>` (+ new caps).

**Done when:** state `green` (every ported feature's acceptance tests pass on v2 and no v2 test that passed
before fails), or `analysed` (analysis and report only: `build=false`, or the v2 stack is not Python +
unittest, code `STACK_UNSUPPORTED`). `escalated` carries the build run's code or `PARITY_REGRESSION`.
